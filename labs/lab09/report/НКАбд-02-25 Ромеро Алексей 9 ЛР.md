# Теоретическое введение {#теоретическое-введение .unnumbered}

## Понятие об отладке

> Отладка --- это систематический процесс выявления, анализа и исправления ошибок (багов) в компьютерной программе. Она выполняется с использованием специализированных инструментов, называемых отладчиками (debuggers), которые позволяют выполнять код пошагово, инспектировать состояние памяти, регистров процессора и переменных во время выполнения. Основные цели включают:

1.  Локализацию первопричины сбоя,

2.  Проверку потока выполнения программы,

3.  Валидацию состояния данных в определённые моменты времени и

4.  Исправление нежелательного поведения без внесения новых ошибок.

> Существует множество методов отладки, среди наиболее часто используемых:

-   **Интерактивная отладка:** Использование отладчика для выполнения программы с точками останова (breakpoints), проверки стека вызовов (call stack) и изменения значений в памяти.

-   **Логирование и трассировка:** Вставка регистрационных сообщений в код для отслеживания выполнения программы и состояния переменных.

-   **Посмертный анализ:** Изучение дампов памяти (core dumps) после серьёзного сбоя.

-   **Удалённая отладка:** Подключение к программе, выполняющейся в другой системе или среде.

> При отладке низкоуровневого кода или двоичных файлов без символов отладки используются специальные методы:

-   **Прямая проверка регистров и памяти:** Инспектирование регистров, таких как EIP/RIP (указатель инструкций), ESP/RSP (указатель стека) и EFLAGS/RFLAGS.

-   **Трассировка стека:** Анализ кадров стека (stack frames) для восстановления последовательности вызовов функций.

-   **Аппаратные точки останова:** Прерывания, генерируемые процессором (INT 3 в x86),

> которые останавливают выполнение по определённому адресу.

-   **Горячая модификация:** Изменение инструкций или значений в памяти во время выполнения для проверки исправлений.

> Такие инструменты, как GDB, WinDbg и radare2, позволяют проводить этот низкоуровневый анализ, что критически важно для реверс-инжиниринга, анализа вредоносного ПО и разработки драйверов.

## Методы отладки

> Методы интерактивной отладки предполагают контролируемое выполнение программы с помощью специализированных инструментов. Основные техники включают:

-   **точки останова (breakpoints)**, которые приостанавливают выполнение на определённых строках.

-   **пошаговое выполнение**, позволяющее продвигаться по одной инструкции (step into) или по одной функции (step over).

-   **инспекцию переменных в реальном времени** с помощью окон наблюдения (watch

> windows).

-   **анализ стека вызовов (call stack)** для отслеживания последовательности выполнения функций.

> Эти инструменты интегрированы в IDE, такие как Visual Studio и Eclipse, а также в отладчики командной строки, такие как GDB и LLDB, что позволяет выявлять логические ошибки, ошибки потока управления и неверные значения.
>
> Методы неинтерактивной отладки, такие как логирование и трассировка, предполагают
>
> вставку инструкций вывода (например, \`printf\`, \`console.log\`) в стратегические точки кода для регистрации значений переменных, сообщений о состоянии и потоков выполнения. Эта техника особенно полезна в средах, где нет доступа к интерактивному отладчику, таких как встроенные системы, рабочие серверы или мобильные приложения. Инструментирование кода с помощью библиотек структурированного логирования позволяет создавать записи, классифицированные по уровням серьёзности (debug, info, error), и облегчает их последующий анализ с помощью инструментов агрегации и поиска.
>
> Для сложных ошибок, таких как утечки памяти, повреждение данных или состояния гонки (race conditions), используются продвинутые методы:

-   **анализ памяти** с помощью инструментов вроде Valgrind, AddressSanitizer или Dr.

> Memory.

-   **отладка потоков (thread debugging)** для выявления взаимных блокировок (deadlocks) и состояний гонки.

-   **обратная отладка (time-travel debugging)**, позволяющая выполнять код как вперёд, так и назад.

-   **анализ дампов памяти (core dumps)** после сбоя программы.

> При разработке драйверов и операционных систем также применяются отладчики уровня ядра, такие как WinDbg/KD, для анализа системных сбоев.

## Реализация подпрограмм в NASM

> Создайте программу lab09-1.asm для вычисления комплексного выражения \$f(g(x))\$, где \$f(x) = 2x+7\$ и \$g(x) = 3x-1\$.
>
> Вля реализации этой задачи применяется принцип модульности с использованием вложенных подпрограмм. Это позволяет разделить вычислительную логику на независимые блоки. Основная программа вызывает подпрограмму \`\_calcul\`, отвечающую за внешнюю функцию \`\$f(x)\$\`. В свою очередь, \`\_calcul\` вызывает вложенную подпрограмму \`\_subcalcul\`
>
> для предварительного вычисления значения внутренней функции \`\$g(x)\$\`. Передача результатов вычислений между подпрограммами осуществляется с помощью регистра EAX, что является стандартным соглашением для возврата значений.

![](media/image3.png){width="6.53125in" height="2.125in"}

> Вы скомпилировали файл и проверили его корректность, используя тестовое значение
>
> \$x = 4\$. Правильность выполнения проверялась шаг за шагом:

-   Ввод: пользователь вводит \$x = 4\$.

-   Преобразование: Программа преобразует строку «4» в число 4.

-   Расчет по формуле: \$f(4) = 2 \\cdot 4 + 7 = 8 + 7 = 15\$

-   Вывод результата: Программа отображает «2x+7=15».

> Программа выдала ожидаемый результат 15, подтверждая правильную работу функции
>
> \_calcul, инструкции mul для умножения, инструкции add для сложения и инструкции ret для возврата из подпрограммы.

## Отладка программ с помощью GDB

Затем загрузите исполняемый файл в отладчик gdb.
>
> ![](media/image4.png){width="6.709031058617673in" height="3.898124453193351in"}

> При работе с отладчиком выполните несколько шагов для анализа состояния процессора:

1.  Запустите программу с помощью команды \`run\`.

2.  Установите точку останова в метке \`\_start\` с помощью команды \`break_start\`, чтобы прервать выполнение до первой инструкции.

> \`layout regs\`. Это разделит окно терминала на разделы, отображающие текущий ассемблерный код, состояние регистров и командную строку.

## Аргументы командной строки в GDB

> Для изучения передачи параметров я скопировал программу из предыдущей лабораторной работы в файл lab09-3.asm и запустил её в отладчике с аргументами командной строки. Особое внимание я уделил анализу стека.
>
> Изучите вершину стека с помощью команды \`x/x \$esp\` (просмотр памяти по адресу
>
> регистра указателя стека) и подтвердите следующее:

-   На вершине стека (адрес по адресу \`\$esp\`) хранится количество аргументов (argc).

-   Следующая ячейка памяти, \`\$esp + 4\`, содержит адрес имени программы.

-   Далее, по адресам \`\$esp + 8\`, \`\$esp + 12\` и так далее, хранятся указатели на сами строки аргументов.

> Шаг смещения составляет 4 байта, поскольку мы работаем с 32-битной архитектурой, где каждый адрес памяти занимает ровно 4 байта (32 бита). Это наблюдение подтверждает теоретическое понимание того, как операционная система передает данные программе при запуске.
